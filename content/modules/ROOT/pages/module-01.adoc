*Objectives:*

[[introduction]]
== Introduction

Building applications using Red Hat Hardened Images is only the first step. 
In this lab, you'll learn how to analyze the security posture of your container images using industry-standard tools.

Two application images are pre-built and waiting for you:

* `rhhi-demo:hardened` — a Flask web app built using Red Hat Hardened Images as the runtime base (`hi/python:3.12`), using the included `pip` to nstall the application dependecies. 
* `rhhi-demo:ubi` — the same Flask app built from the standard UBI10 base image (`ubi10/ubi`) with Python 3.12 and pip installed via dnf, a common real-world pattern for containerizing Python applications

Both images run the same application code and the same version of Python 3.12. 
The only difference is the base image. 
You'll use `grype` to scan both for known CVEs and see firsthand how the choice of base image affects your security posture.
You'll also create and explore the Software Bill of Materials (SBOM) for a container image in a later section.

[[podman-socket]]
== Step 1: Enable the Podman Socket

Grype and Syft use the Podman API socket to find and inspect images. 
As a rootless user, you can enable this socket just for your session — you don't need system-level access.

[source,bash,role=execute]
----
systemctl --user enable --now podman.socket
----

[NOTE]
====
This enables the socket for the current user session only. It does not require `sudo` or root privileges. This is a key feature of rootless Podman: the daemon socket runs entirely within your user namespace.
====

[[scan-hardened]]
== Step 3: Scan the Hardened Image

Use Grype to scan `rhhi-demo:hardened` for known CVEs:

[source,bash,role=execute]
----
grype rhhi-demo:hardened --by-cve
----

[NOTE]
====
The scan may take 1-2 minutes to complete. The `--by-cve` flag normalizes output to CVE identifiers instead of other data sources like GHSA, making it easier to cross-reference with other tools and databases.
====

.*Expected output (varies, but typically):*
----
 ✔ Loaded image                                           rhhi-demo:hardened
 ✔ Parsed image sha256:9b2e4f6a...
 ✔ Cataloged contents  a3c7d9e1...
   ├── ✔ Packages                        [68 packages]  
   ├── ✔ File digests                    [3,064 files]  
   ├── ✔ Executables                     [184 executables]  
   └── ✔ File metadata                   [3,064 locations]
 ✔ Scanned for vulnerabilities     [0 vulnerability matches]
   ├── by severity: 0 critical, 0 high, 0 medium, 0 low, 0 negligible
   └── by status:   0 fixed, 0 not-fixed, 0 ignored
No vulnerabilities found
----

[NOTE]
====
Hardened base images typically have **zero or near-zero CVEs** at ship time. Results may vary slightly over time as new CVEs are discovered against any component.
====

[[scan-ubi]]
== Step 4: Compare with the UBI Image

Now scan the UBI-based version to see the difference:

[source,bash,role=execute]
----
grype rhhi-demo:ubi --by-cve --only-fixed
----

.*Expected output (varies, but typically):*
----
 ✔ Loaded image                                           rhhi-demo:ubi
 ✔ Parsed image  sha256:8f3a1c2d...
 ✔ Cataloged contents   c4b8e2f5...
   ├── ✔ Packages                        [~150 packages]
   ├── ✔ Executables                     [~200 executables]
   ├── ✔ File metadata                   [~3,000 locations]
   └── ✔ File digests                    [~3,000 files]
 ✔ Scanned for vulnerabilities     [vulnerabilities found]
   ├── by severity: N critical, N high, N medium, N low, 0 negligible
   └── by status:   N fixed, N not-fixed, 0 ignored
<output truncated>
----

[source,bash,role=execute]
----
grype rhhi-demo:ubi --by-cve --only-fixed
----

[NOTE]
====
The `--only-fixed` flag shows only vulnerabilities that have available patches. This focuses attention on immediately actionable issues rather than `wontfix` items. Remove the flag to see the full vulnerability list including unfixed issues.
====

**Key Insight:**

* **Hardened image** (`rhhi-demo:hardened`): Minimized image tracking upstream to deliver new images as quickly as changes are available.
* **UBI image** (`rhhi-demo:ubi`): General purpose base image tracking RHEL to deliver backported fixes for maximum flexibility and supportability.

Both images run the same Flask app on the same Python. 
The CVE difference comes entirely from the base image — the hardened runtime includes only what a Python application needs at runtime, while even a minimal UBI base carries package management infrastructure and general-purpose system tools. 
Every extra package is a potential CVE surface.
Within the UBI family, there are additional types beyond the standard image used here that also address this sort of package reduction.

Both images include the Python dependecies for Flask (`pip install flask`), so any CVEs in the application would be common.

[[summary]]
== Summary

The choice of starting point can greatly impact the amount of triage required by teams to secure an application.
While this is not the only factor when considering base image choices, it's important to understand how the different life cycle choices influence the results.
